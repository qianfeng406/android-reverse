# D5 修复规划与 D6 实施验证设计

## 目标与阶段交接

| 阶段 | 输入 | 处理 | 输出 |
| --- | --- | --- | --- |
| D5 | 原始 ELF、D0 指令/CFG、D2 选定结构、D4 规则及未解项 | 检查可替换指令、分支距离、分发路径副作用与目标块活跃输入；为可安全恢复的边生成最小 ARM64 修改 | `patch_plan.json`，含每个来源的安全审计、旧/新字节、目标、证据和未解原因 |
| D6 | 原始 ELF、D5 计划、测试输入与运行器 | 在新文件上核对旧字节并执行修改，重建 CFG，比较原件与副本的行为，试验撤销 | 修复 `.so`、修复 CFG、`verification_report.json` |

两阶段使用 `binary_id`、函数、D4 `plan_id` 和输入哈希识别同一分析版本。D5 可以保留未解项，但 D6 默认只接受**所有待恢复来源都 ready、没有字节冲突**的计划。D5 的模型建议可作为单独审查意见，不能把失败的安全检查改为通过。所有文件修改仅作用于副本。

## D5：先证明可跳过，再选择补丁

首版 `arm64_direct_edges_v1` 只处理 demo 的三种来源。条件边的第一/第二目标与 D4 的 `guard_ast`、状态、`route_path` 一一对应。

| 来源 | 保留的计算 | 拟改指令 | 新流程 |
| --- | --- | --- | --- |
| 入口初始状态 | 栈帧建立等原有指令 | 将初始状态 `STR` 改成 `B target` | 入口直接到首个执行块 |
| 单后继业务块 | 包括状态写入在内的原有指令 | 将块尾 `B hub` 改成 `B target` | 原计算后直接到后继 |
| 双后继业务块 | 原条件计算与 `CSEL` | 将状态 `STR` 改成 `B.cond true_target`，块尾 `B hub` 改成 `B false_target` | 按原条件直接到两个后继 |

双后继模板要求原 `CSEL` 使用与 D4 真分支相同的条件码，`CSEL` 与被替换的 `STR` 之间没有改写 NZCV 的指令，`STR` 后紧接可替换的无条件 `B`。条件分支使用原始比较结果；被删的是分发状态的内存写入。若模板、分支范围或指令空间不匹配，输出未解，不能猜一个跳板。

副作用审计必须逐条核对每个 `route_path` 中将被绕过的指令。首版只允许纯比较、状态搬运、直接分支，以及仅供分发区域内部读取的状态别名栈槽写入。调用、异常、未知内存写入、SP 改变、跳过后仍被业务块读取的寄存器/内存/标志均阻止 ready。对于 `sp+0` 这类状态别名，检查其所有静态读取都在分发区域内；若无法证明，保留未解。D4 的 `static_proven` 只证明路径与状态映射，**不等于**可跳过这些指令。

`patch_plan.json` 的核心契约：

```json
{
  "strategy": "arm64_direct_edges_v1",
  "function": "lesson_score",
  "plan_id": "<D4 plan_id>",
  "input_hashes": {"instruction_table": "<sha256>", "static_cfg": "<sha256>",
                   "structure_candidates": "<sha256>", "transition_rules": "<sha256>"},
  "entries": [
    {
      "source_block": "0x17e0", "kind": "conditional", "status": "ready",
      "targets": ["0x1804", "0x182c"],
      "patches": [
        {"site": "0x17fc", "old_bytes": "<8 hex>", "new_bytes": "<8 hex>",
         "kind": "b.cond", "condition": "eq", "target": "0x1804"},
        {"site": "0x1800", "old_bytes": "<8 hex>", "new_bytes": "<8 hex>",
         "kind": "b", "condition": null, "target": "0x182c"}
      ],
      "audit": {"passed": true, "checks": ["<具体证据>"], "skipped_blocks": ["0x18f8", "0x1620"]},
      "evidence_refs": ["insn:0x17f4", "insn:0x17fc"]
    }
  ],
  "unresolved": []
}
```

真实产物可增加说明字段，但不能改变上述字段含义。`old_bytes` 来自原件指令表，`new_bytes` 是小端 ARM64 指令字；补丁点按模块虚拟地址表示，D6 通过 ELF 节映射到文件偏移。每项修改都包含撤销所需旧字节。指令编码器须检查 4 字节对齐和 `B`/`B.cond` 的有符号位移范围。

## D6：实施、CFG 与行为验证

1. 复核原件 SHA-256、D5 输入哈希、各补丁点旧字节及补丁互不重叠；以原件创建新文件并一次性写入全部补丁。失败时删除临时文件，不触碰原件。
2. 用 Capstone 从新文件重解目标函数，调用现有 CFG 建图逻辑；核对每个补丁点解码的类型、条件码和目标与计划一致。导出 `patched_instruction_table.json`、`patched_cfg.json` 或等价的版本化产物，并统计入口可达的分发块数。
3. 验证撤销：把副本上的 `new_bytes` 换回 `old_bytes`，其 SHA-256 必须等于原件。原件哈希在整个过程保持不变。
4. 用可重复的运行器分别加载原件和修复副本，按同一组输入收集返回值、退出码和标准错误；比较两份记录。首版对 `lesson_score(int32_t)` 使用设备上的 Android runner。运行器参数和输入组保存到报告；失败定位到输入与补丁计划。

`verification_report.json` 至少包含原始/修复文件哈希、计划哈希、补丁应用及撤销检查、CFG 变化、逐输入行为对比、失败与未覆盖范围。七组已知输入及额外边界输入的相同返回值只证明这些测试点；不能声明所有输入的形式化等价。若设备不可用，可先运行静态检查并明确把行为验证记为 `not_run`，不能报 demo 已完成。

## Demo 验收

- D5 为入口及 12 个状态写入业务块生成可审阅计划；四个双后继来源各有两条目标，无法确认副作用时不得 ready。
- D6 的修复 `.so` 可独立在 Android runner 中加载；入口可达的分发区域为 0，业务块间直接边与计划相符。
- 原件未改；撤销后的哈希与原件相同；规定输入的返回值及可检查副作用一致。随机或额外输入扩大经验覆盖，但不代替副作用审计。
- 模型复核只读，固定测试与保存的运行结果可在干净环境重放。原始设备日志和修复 `.so` 留在忽略的 `work/`，仓库提交代码、文档和小型测试夹具。

## D5/D6 可达路径清理

D5 先模拟真实边补丁并重建 CFG，再生成独立的 `cleanup` 子计划。首版只处理：跳向下一指令的 `B`、单入口的条件跳板、无可达别名读取的状态栈槽写入，以及目标寄存器在所有可达后继均不活跃的 `MOV/MOVK/CSEL`。栈槽证明要求固定栈帧、已知访问宽度、栈地址不逃逸且没有未知控制流。无法证明的候选记录在 `cleanup.unresolved`，不阻止已安全的真实边补丁。

D6 对清理计划重新运行数据流证明并核对旧/新字节、分支条件和目标，然后在副本上应用两层补丁、重解指令、验证回滚及设备行为。报告分别保存完整 CFG、入口可达 CFG 和仅供展示的 NOP 节点折叠图；展示图不代表二进制中的实际块数。原位 `NOP` 不缩小 ELF 或函数符号范围。
