# 动态扩展与 D7 质检设计

**状态：设计稿，尚未实现。** 本文为后续子 agent 开发提供阶段契约和验收标准。当前 D0–D6 的实现与限制以 [开发文档](DEVELOPMENT.md) 和 [使用说明](USAGE.md) 为准；本文的 `attempt_id`、自动重跑、D7 和规则晋升均是拟议能力。

## 1. 目标与边界

目标是在已有静态分析、动态采集、补丁验证的基础上，对新混淆机制形成可追踪的迭代：发现缺口 → 取证 → 提出临时策略 → 确定性校验 → 从受影响阶段重跑 → 质检。这里的“动态扩展”指分析策略和采集计划随证据迭代，不承诺任意样本都能自动解混淆。

首个验收对象仍是**已知目标函数**的 Android ARM64 ELF。非导出函数、未知签名、递归、间接 `BR/BLR`、多局部分发器、跨函数状态更新、外部副作用等分别作为后续能力扩展；不在尚无采集或证明能力时默认视为支持。原件只读，补丁只写副本。

设计原则：原始 trace 和指令是事实；结构、转移与修复是可撤销假设或证明；模型输出是提案。任何观察到的路径不能直接升级为全输入规则，任何模型建议不能直接升级为 `static_proven`、`ready` 或 `passed`。

## 2. 目标流水线

```text
D0 样本基准 → D1 粗 trace → D2 结构候选 → D3 定点采集
                                    ↓                 ↓
                              失败分类与策略循环 ← D4 转移推导
                                    ↓                 ↓
                              按依赖重跑       D5 修复规划 → D6 实施验证
                                                        ↓
                                               D7 通用质检＋模型审阅
                                                        ↓
                                      通过 / 补采或重分析 / 人工复核
                                                        ↓
                                               临时规则晋升评审
```

各阶段仍可单独运行。新增 `orchestrator` 只负责读取阶段产物、选择下一动作、保存迭代记录，不把阶段逻辑搬进调度器。失败不一定回到 D4；回退位置由原因码和证据确定。

| 阶段 | 固定输入 | 扩展点 | 输出及成功条件 |
| --- | --- | --- | --- |
| D0 | 原始 ELF、目标函数定位、反汇编来源 | 函数定位与签名适配器 | `binary_manifest`、指令表、CFG；版本与范围一致 |
| D1 | D0、触发目标的运行环境 | 入口定位、事件采样、调用边界和参数适配器 | 带线程/调用 ID 的原始 trace、采集质量报告 |
| D2 | D0、D1 | 结构策略与原子证据规则 | 候选、反例、区域归属和初步探针需求；至少一个可审查候选 |
| D3 | D2、D0、同轮运行 | 状态/条件/间接目标探针规划器 | 统一 `transition_observations`；每次观测可配对、缺失显式记录 |
| D4 | D0、D2、D3 | 指令语义、跨块切片、路由解析策略 | 带条件和证据的规则；待自动修复的边须静态证明 |
| D5 | D4、D0、D2 | 补丁模板、副作用/活跃值审计、清理策略 | 真实边计划与独立的可选清理计划；未证实项保持未解 |
| D6 | D5、原件、runner | 行为与副作用比较器、修复前后 trace 比较 | 修复副本、完整/可达 CFG、差分与回滚报告 |
| D7（新） | D0–D6 及产物索引 | 质量检查器、必经模型审阅、问题路由 | `quality_report`、可核查问题单、重跑建议和规则晋升建议 |

### 2.1 阶段产物版本

保留现有 `binary_id + module_offset`、证据引用和输入哈希。新增一次分析的 `analysis_id`，每次尝试的 `attempt_id`、所选策略的 `strategy_id/version/config_hash`、输入产物哈希与父尝试 ID。一次重跑产生新产物，不覆盖旧证据；旧采集可复用仅当目标版本、结构 ID、探针计划 ID 与归一化契约一致。修改 D2 候选或 D3 探针后，旧 D3 观测不能默默拼接。

建议新增 `artifact_index.json`：每个阶段记录路径、哈希、产生它的命令、策略版本、依赖哈希及状态。`stage` 校验保留为确定性闸门；调度器读取索引决定最早需要重跑的阶段，而非凭文件时间判断。

## 3. 统一反馈与重跑

### 3.1 失败和质量缺口分开

每阶段产出统一 `issues[]`，至少包含以下字段：

```json
{
  "code": "cleanup_unknown_instruction_effect",
  "severity": "quality",
  "stage": "D5",
  "scope": {"function": "route_score", "sites": ["0x1968"]},
  "evidence_refs": ["insn:0x1968", "artifact:patch_plan"],
  "blocking": false,
  "retry_from": "D5",
  "action_kind": "extend_instruction_effect",
  "status": "open"
}
```

`blocking` 表示无法进入安全补丁；`quality` 表示可生成修复副本，但可读性或覆盖度不足。D5 的 `patch_plan.unresolved` 和 `cleanup.unresolved` 必须分别映射：第二个 demo 的 19 处死状态写入属于后者，不能因为 D6 行为通过而消失。采集基础设施故障、证据不足、当前策略不支持和真实矛盾也要分别编码。

| 代表原因 | 首选动作 | 最早重跑阶段 | 必须保留的证据 |
| --- | --- | --- | --- |
| ELF/设备版本不一致、函数范围错误 | 修正输入；重采 | D0 或 D1 | 哈希、符号/范围、设备模块信息 |
| D1 未命中、丢事件、覆盖不足 | 调整触发和采样；增量采集 | D1 | 调用边界、输入、缺失事件 |
| D2 无候选或候选冲突 | 换规则组合、补结构策略或 D1 输入 | D2；必要时 D1 | 候选评分、反例、图切片 |
| D3 缺探针能力或配对失败 | 补规划器、换探针或重采 | D3 | `plan_id`、原始 JSONL、缺失项 |
| D4 未知条件/状态/间接目标 | 补语义或切片策略；必要时补 D3 | D4 或 D3 | 指令切片、表达式 AST、观测冲突 |
| D5 模板/副作用不明 | 补模板与审计；不得猜测跳过代码 | D5；必要时 D4 | 待跳过指令、目标活跃输入 |
| D5 清理未解 | 作为质量缺口；补纯指令/别名分析 | D5 | 未解清理点、残留状态读写 |
| D6 行为差异 | 先定位首个路径或副作用差异 | D5/D4/D3/D2，依证据 | 输入、返回/副作用、前后 trace |
| D7 发现残留结构或语义疑点 | 生成问题单并定位责任阶段 | 对应最早阶段 | CFG、反编译切片、证据引用 |

### 3.2 调度状态机

状态：`ready → running → issue_detected → proposal_pending → proposal_validated → retry_ready → running`，直到 `quality_passed`、`needs_human_review`、`budget_exhausted` 或 `unsupported`。每轮只处理有证据的最早阻塞项；不同问题可成批，但不能在依赖产物过期时并行推进下游。支持“仅从 D5 重跑”和“D2 改动后重新编译 D3 计划”等依赖传播。

循环上限按**次数、模型调用、采集次数、设备时长**分别配置。相同 `binary_id + issue_code + evidence_hash + strategy_config_hash` 再次出现且无新证据时停止循环，避免模型重复回答。每轮记录新增/消除的问题、规则变化和成本；新尝试让已证明边减少或行为回归失败时撤回该临时策略。

## 4. 策略与模型接口

### 4.1 策略单元

策略注册表统一描述 `strategy_id`、版本、所属阶段、支持的架构/指令/状态位置/转移类型、所需证据、输出契约和不支持原因。原子证据规则用于组合判别，机制策略负责跨块、间接跳转等完整算法；不能靠改变 D2 七条证据规则来冒充新机制。D3 应依据 D2 候选和能力声明选择规划器；D4 与 D5 使用匹配的机制/补丁策略，不再在调度入口固定写死首版策略。

临时策略存于当前实验的 `strategy_overrides`，带版本、来源 issue、适用范围、参数与测试记录。参数化匹配优先于按地址写例外；含特定函数地址或状态常量的规则必须标记 `sample_specific`。策略未通过接口、静态审计和旧样本回归前不得进入默认库。

### 4.2 模型的三个调用点

1. **阻塞诊断：**D2–D6 按 `issues[]` 请求有限且相关的指令、图、观测切片，返回原因假设、应补的证据、已登记策略/参数或新策略规格。
2. **重试审阅：**临时策略应用后对比前后 issue、规则、补丁和行为；模型只指出异常，不能把失败状态改为通过。
3. **D7 必经审阅：**每次完成 D6 后检查修复图、残留状态作用、未解项、差分及可用反编译证据；返回有证据的问题和优化机会。

沿用 `codex_exec` 和 `replay` 适配器，模型配置沿用 `gpt-6-sol/high`；所有请求/响应保存为可重放产物。模型超时、不可用或引用无效时状态为 `review_pending` 或 `needs_human_review`，不能伪称 D7 已通过。模型提案经过 Schema、地址范围、引用、策略能力和回归验证；可执行补丁字节不得直接取自模型回复。若模型建议“新增语义”，应形成有明确指令效果、前置条件和反例的策略任务，经开发与测试后再重试。

模型上下文以问题为中心取切片，并提供按引用补取证据的只读适配器；目前只截取有限指令和观测，遇跨块/跨函数问题可能不够。IDA MCP 或等价静态导出可作为证据来源，但不要求模型直接修改 IDA 数据库。

**自动重试的权限边界：**模型选择已登记策略、调整已声明参数或提出合法探针时，可以经 Schema 与能力检查后自动创建新 `attempt`。模型提出新的指令语义、补丁模板或可执行代码时，只生成开发任务；完成实现、测试和代码审阅前，循环停在 `needs_human_review`。这样“多次循环”能自动处理已支持策略的组合与补采，新增机制则通过子 agent 开发策略后续接，而不是在运行中的样本上执行未经审计的模型代码。

## 5. D7 质检契约

D7 的输入为 D0–D6 的当前有效产物、修复副本、原件、测试/采集覆盖信息，以及可选的 IDA 反编译结果。先执行确定性检查，再**必须**请求模型审阅。输出 `quality_report.json`：

| 字段 | 内容 |
| --- | --- |
| `identity` | 样本、函数、尝试、各阶段产物哈希和策略版本 |
| `structural_checks` | 真边来源覆盖、未知控制流、可达分发区域、残留状态读写、可达与全量 CFG、死块情况 |
| `semantic_checks` | 原件/副本返回和已声明副作用差分、trace 首个差异、未覆盖输入与路径 |
| `readability_checks` | 可达非 NOP 指令、可达块、未解清理点；反编译成功与否及证据来源 |
| `model_review` | 必经调用状态、引用完整的问题、待验证建议、模型与请求哈希 |
| `issues` | 分类、严重度、责任阶段和下一轮动作 |
| `status` | `passed`、`retry_required`、`review_pending`、`needs_human_review` 或 `failed` |
| `promotion_candidates` | 临时策略的通用性评估与所需回归，不直接写默认策略库 |

硬闸门：产物哈希一致、D6 补丁可回滚且行为检查无已知差异、拟修复边均有证明、无未解释的可达间接边或关键副作用。覆盖不足、未解清理、IDA 反编译失败等分别计入质量问题；它们是否阻止 `passed` 由公开的质量配置决定，不可用一个模糊“CFG 好看”指标代替。无运行器或模型不可用时只能 `review_pending`/`needs_human_review`。

模型的问题必须被转为可核查 issue：指向具体地址、边、观测或反编译行，且经过引用校验。无法验证的建议保留为意见，不自动触发 patch。D7 可以要求回到 D1 增加覆盖、D3 补采、D4 重推、D5 补清理，或要求人工审阅；重跑后整个 D6/D7 必须重新执行。

### 5.1 临时规则晋升

D7 只提出 `promote`、`keep_local`、`reject` 建议。晋升由独立回归门槛决定：规则使用可解释的机制条件而非样本地址/常量；保存正例与反例；新样本和既有样本回归无误判；不会降低已有证明和副作用审计；记录性能与采集成本。规则的代码审阅和合入仍属项目维护流程，不能由单次样本的 D7 自动提交。晋升与当前样本质检通过是两个独立结果。

## 6. 开发里程碑与子 agent 任务

每个任务只修改列出的模块与契约，先交测试和可重放产物，再交下一任务。负责人在合并前核对跨阶段接口与 demo 回归。

| 顺序 | 子任务 | 交付物 | 验收重点 |
| --- | --- | --- | --- |
| M0 | 契约与夹具 | `issues`、`artifact_index`、`attempt`、D7 Schema；现有两个 demo 的迁移/兼容测试 | 旧数据可读，哈希和来源可追踪，旧运行不被覆盖 |
| M1 | 采集能力声明 | D0/D1 目标定位和签名配置；D3 策略选择接口及不支持报告 | 已支持目标仍可采；非导出/未知签名明确失败或降级，不能伪造值 |
| M2 | 分阶段策略调度 | D2/D3/D4/D5 注册能力与统一选择；机制策略和原子规则分层 | 未知策略保留未解；新策略可插入而不改统一产物语义 |
| M3 | 反馈分类与重跑 | 问题归一化、依赖失效、从最早阶段重跑、轮次/成本和重复检测 | 注入 D2/D3/D4/D5/D6 故障，回退到正确阶段；旧证据不串轮 |
| M4 | 模型提案闭环 | 结构化请求、引用补取、提案校验、临时规则配置/重试审阅 | replay 可重现；无效提案不改变状态；模型故障明确停止 |
| M5 | D6 验证增强 | 可选修复前后 trace 差分、可配置副作用比较、失败定位 | 能指出首个可靠差异；未采集不能标记“相同” |
| M6 | D7 | 通用质量指标、必经模型审阅、问题路由、质检状态 | 第二个 demo 的残留状态写入旧结果触发质量 issue；新结果通过；模型不可用不误报通过 |
| M7 | 规则晋升 | 临时策略范围分类、跨样本回归清单及建议报告 | 硬编码规则保持本地；通用规则须有正反例和旧样本回归 |

最小纵向演练：从第二个 demo 的**旧 D5 产物**注入 `cleanup_unknown_instruction_effect`，经模型或 replay 建议补指令作用，重跑 D5→D6→D7，观察状态写入 19→0；再用人为制造的 D3 探针不支持项验证回退 D3，不可一律回 D4。随后选一类新机制样本作为首次外部泛化测试。每项都记录误判、剩余未解、模型调用次数、采集/运行时间和产物哈希。

交付给子 agent 的每项任务需同时说明：负责的阶段与文件、读取的上一阶段契约、写入的产物 Schema、支持和拒绝的机制、重试时哪些产物失效、固定正反例、设备实验条件。验收先跑对应阶段测试，再跑两个旧 demo 的离线重放；涉及采集或二进制修改时，再做设备差分。文档与使用说明随实现更新，不能只提交策略代码。

## 7. 当前实现与计划的差距

现有 D2 只有一项机制策略，D3 的规划器在入口固定选择 `stack_slot_v1`，D4 只有对应推导策略，D5 固定直接边模板。`on_blocker` 是可选只读诊断，不回写规则、不调度重跑，且 D5 不检查 `cleanup.unresolved`。D6 尚无 trace 差分、完整外部副作用检查或 IDA 可读性审阅；`stage` 当前只接受 0–6。故 M0–M6 均是开发任务，不能因当前两个 OLLVM 样本通过而标成已完成。
