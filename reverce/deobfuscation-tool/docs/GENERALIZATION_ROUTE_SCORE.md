# 第二个样本：route_score 泛化测试

2026-11-23，在 Kali `192.168.24.142` 使用现有经典 OLLVM `opt -O0 -fla` 构建 [route_score](../examples/route_score/README.md)。目标函数含两个循环、嵌套分支和三种返回路径；同库 `route_identity` 独立编译。工具未预填新函数的块地址、状态槽或业务块名单，也未为本样本改写识别规则。原始产物和逐条命令保存在本机 [实验目录](../work/experiments/route-score-20261123/RUNBOOK.md)，该目录由 Git 忽略。

| 对照 | 未混淆 `route_score` | 平坦化版本 |
| --- | ---: | ---: |
| 函数大小 | 460 字节 | 1784 字节 |
| ARM64 指令 | 115 | 446 |
| 静态基本块 | 28 | 96 |

本轮平坦化 ELF 的 SHA-256 为 `a18718c4858239aa9b8873e8985f0c824e7be93dcd74d08b1360e5f6f0f34e91`。设备上的同名库与本地哈希一致。原件与未混淆对照在 12 个输入上返回值一致，包括 `INT32_MIN`、`INT32_MAX`、负数和分支边界附近的值。

| 阶段 | 实际产出 | 评价 |
| --- | --- | --- |
| D0/D1 | 9 次函数调用，22,468 条原始事件；静态导出 446 条指令、96 块 | 通过 |
| D2 | 5 个候选，选中共享回跳 `0x1d18`；选中候选标注 64 个分发块、31 个执行入口 | 结构候选可用，尚属假设 |
| D3 | 31 个来源、43 个探针；731/731 条转移记录完整，731 条分发读取，未配对 0 | 通过 |
| D4 首轮 | 32 条规则、39 个选项；4 个来源未解 | 停在指令语义支持范围 |
| D5/D6 首轮 | 27 个 ready 来源、38 条候选补丁；D6 报 `incomplete plan` | 正确拒绝部分 patch |

D4 首轮的四个阻塞点是 `0x1968 MVN`、`0x1A5C AND`、`0x1C10 LSR`、`0x1CF0 MUL`，均位于业务运算中，后续 `MOV/MOVK` 会覆盖目标寄存器并写入状态槽。首轮解释器遇到它们即停止整块证明，D5 随之保留未解，D6 因计划不完整而拒绝实施。

D6 的拒绝提示现会给出未解来源数量和第一个来源/原因，并指向 `patch_plan.json` 与 `unresolved_rules.json`。责任回路为 D4 补转移证明、D5 重做补丁规划、D6 再验证；D6 不从动态轨迹猜补丁。

本轮按 `on_blocker` 触发了两次只读模型诊断：D4 建议增加指令语义策略，并指出 `0x1964` 缺少动态观测；D5 指出相关运算结果参与业务值的写入，不能跳过这些计算。模型意见没有修改转移规则或补丁状态；完整请求与回复保存在 `results/model_diagnostic_reviews.json`。

针对该问题已扩展 D4 的抽象执行：上述四类指令把目标寄存器值标为未知，继续追踪后续状态写入；若未知值参与状态或条件，规则仍保持未解。业务指令本身保留在修复库中。D4、D5、D6 用同一份冻结的 ELF、反汇编和 trace 重新运行，成功产出修复库。D6 的静态 CFG 为全量 107 块、入口可达 43 块，展示图折叠 NOP 节点后为 32 节点；可达非 NOP 指令经清理从 257 降到 188。70 个可选清理候选因 `unknown_instruction_effect` 等证据不足被保留，其中状态槽可达写入仍有 19 处。测试输入一致不能替代全输入等价证明。

这一结果证明缺口位于 **D4 指令语义处理**；D5 负责接收完整规则并做跳过副作用审计，D6 负责拒绝不完整计划和验证成品。后续若要进一步改善反编译可读性，应扩展 D5 清理审计的指令作用模型，仍须保持未知效果时不自动删除。

## 2026-11-24：残留状态更新的原因与修复

进一步检查发现，D4 已完整证明真实边，D6 也确认入口可达分发块和状态槽读取均为 0。残留的 19 处 `STR W8, [SP,#0x10]` 属于 D5 的**死状态写入清理**缺口，不是 D4 未识别转移。D5 清理器独立维护可识别指令集；可达业务块中的 `MVN`、`AND`、`LSR`、`MUL` 共四处不在该集合内。它以全函数安全闸门处理未知指令，因此把全部 19 处状态写入标为 `unknown_instruction_effect`，并连带保留许多构造状态的寄存器写入。原报告中 70 个可选未解项由这 19 项和 51 项 `register_destination_live_or_unproven` 组成；不能将 19 项误解为 19 条未知指令。

已将这四类无内存副作用的寄存器运算加入 D5 的指令作用模型与死寄存器写入分析。用同一份冻结 ELF 和 D0–D4 产物重新运行 D5/D6，19 处状态写入全部清理；可达非 NOP 指令 **188→121**，可达基本块仍为 43，入口可达分发块仍为 0。保留 7 项 `register_destination_live_or_unproven`，不在证据不足时继续删除。新修复库、补丁计划、12 组设备差分和回滚检查保存在本机 [route-cleanup-20261124](../work/experiments/route-cleanup-20261124/)；D6 状态为 `passed`，12/12 输入一致。有限输入一致不构成全输入形式化等价证明，也未替代 IDA 反编译审阅。

本次 `on_blocker` 未因清理缺口调用模型：D5 的模型触发器只检查真实边规划的顶层 `unresolved`，没有检查 `cleanup.unresolved`；D6 的行为检查已通过。这说明当前反馈机制把“能够安全修复真实边”和“清理后的可读性”当作同一个通过结果。后续可将清理质量作为独立报告项，在未知指令阻挡死状态清理时提供只读模型诊断和策略建议，仍由确定性验证决定是否删除指令。
