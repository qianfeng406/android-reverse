# 大模型介入设计核查

## 1. 结论与调用模式

**D0–D6 没有必须在每次运行中调用大模型的阶段。** 已知混淆模式由确定性策略处理，证据不足时输出 `unresolved`。模型的用途是给未知结构、未解语义或验证失败提出**可核查的下一步**，不能把观察升级为证明，也不能直接批准或执行补丁。

若产品目标是让工具在**尚未登记策略的新变种**上自主提出扩展方向，就需要保留统一的模型接口或同等的人工审查入口；这属于扩展能力的入口，不是单个样本运行的必经计算步骤。

当前代码只有两种显式调用：`discover --use-model` 对 D2 结构候选作一次只读提案，并允许模型选择已登记的可选证据规则；`review-rules --source ... --use-model` 对指定 D4 转移规则提出疑点和补采点。两者都需用户在命令中启用，D2 的核心规则始终执行，D4 审查不会改写规则。D3、D5、D6 尚无模型调用入口。

D2 当前先由规则引擎发现候选，再把摘要送给模型；模型提议的区域本身不会直接替换选定候选，只会通过已登记规则的选择触发重新计算。D4 的审查结果单独存档，也不会自动形成新的探针计划。这些是当前接口的实际边界。

后续建议保留三种运行策略：

| 模式 | 调用时机 | 适用情况 |
| --- | --- | --- |
| `off`（默认） | 从不自动调用；按规则运行并保存未解项 | 固定测试、成本可控的批量分析 |
| `manual`（当前已有的显式命令） | 分析人员指定阶段和来源后调用 | 审阅单个候选、调试规则 |
| `on_blocker`（待实现） | 确定性检查确认有可分析的阻塞项时调用 | 新变种的策略扩展和失败诊断 |

即使启用 `on_blocker`，**阶段成功时不调用模型**。调用失败、超时或提案被校验拒绝时，保留原有未解状态；不能因模型不可用而猜测后继或 patch。

## 2. 各阶段的触发规则

下表中 D2、D4 的手动入口已实现；自动触发和其他阶段的模型任务均为设计，尚未实现。

| 阶段 | 先执行的确定性处理 | `on_blocker` 的触发条件 | 模型只可提出 | 不调用模型的情况 |
| --- | --- | --- | --- | --- |
| D0/D1 | 校验二进制、函数范围、指令及 trace 完整性 | 无 | 无 | 哈希不符、采集缺失、设备离线等应修复输入或重采 |
| D2 | 原子规则建图、筛选候选、生成探针计划 | 无候选；或不同 hub/状态槽的候选在状态写入块数、比较块数、fan-in 三项上并列，现有证据无法区分 | 候选区域、状态位置、已登记规则组合或下一轮采集建议 | 单一候选证据闭合且可编译探针 |
| D3 | 编译探针并归一化同轮采集 | `compiled_probe_plan.unsupported` 含不支持的状态/探针形式，或静态来源无法布点 | 已有指令位置上的探针建议、需新增的采集策略说明 | 探针事件丢失、乱序、进程未命中：先重采，不交模型猜数值 |
| D4 | 符号解释、分发路径求值、与观测核对 | `unresolved_rules` 含未知指令/条件/间接目标；或完整重采后仍有 `contradicted` | 语义假设、补采位置、可检验的新策略说明 | 全部规则已静态证明；仅有某条边尚未在有限输入中观察到不构成阻塞 |
| D5 | 模板匹配、副作用与活跃值审计、编码检查 | 未解原因是未知副作用、混合块或现有模板不能保留必要计算 | 保留哪些指令、可能的新模板和需核查的活跃输入 | 旧字节不符、输入过期、地址越界：直接修正工件或实现编码策略 |
| D6 | 核对补丁、重建 CFG、撤销哈希与运行差分 | 静态检查通过但真实运行出现返回值差异或崩溃，确定性差异定位仍无法解释 | 首个差异点的原因假设、建议的 trace/探针与回归输入 | 设备不可用、runner 缺失、哈希不符；全部检查通过 |

D2 的“并列”应按现有排序所用的前三项证据比较，不把地址排序视为可信度。D3/D4 的观测冲突先排查 binary_id、plan_id、事件配对及采集完整性。D6 需要先增加可选的修复前后 trace 采集，模型才可能基于路径差异定位；当前只有逐输入返回值等事实。

实现 D2 的“无候选”触发时，请求必须从观察图和静态指令构造摘要；当前 `discover --use-model` 主要截取已有候选附近的指令，不能原样用于无候选诊断。

## 3. 如何调用与交接

当前实现通过 `ModelAdapter` 启动**独立的** `codex exec` 进程，使用 `config/default.toml` 的 `gpt-6-sol`、`high`，只读工作区和 JSON 输出 Schema；它不继承当前聊天的上下文。也支持保存完整请求与提案后离线 `replay`。后续的按需任务复用这一适配器，但按任务使用各自的输入/输出 Schema。

每次请求至少包含 `binary_id`、阶段、阻塞原因码、来源块或规则 ID、相关产物哈希、有限的指令/观测切片及允许引用的证据 ID。响应只包含带证据引用的假设、已知策略参数、建议探针或下一次实验。请求与响应一同保存，按请求哈希去重；每个阻塞项限制调用次数和输入大小，避免把整份 trace 送给模型。

处理提案的固定顺序为：

1. 校验 JSON Schema、二进制/来源身份、证据引用及地址范围。
2. 将提议的**已登记**规则或探针参数交给 D2/D3 的确定性编译器重新运行；D4/D5 重新做静态证明与安全审计。
3. 若提案需要新指令语义或新修复模板，将它记录为策略开发任务；新增策略经测试和样本验证后再登记。模型生成的代码或补丁字节不直接投入目标进程。
4. 对新产物保留原证据、提案、复核结果和反例。失败时仍输出 `unresolved`，供人工或下一轮采集处理。

IDA MCP 可为请求提供已导出的函数、指令和交叉引用，但仍需转换为版本化证据。模型建议不直接操作 IDA 数据库或 `.so`。D5/D6 的 `ready` 和 `passed` 只能由审计、编码、CFG 与运行检查产生。

## 4. 对当前 demo 的判断

`lesson_score` 的已知比较链与栈状态槽在规则策略内闭合：D2 有候选，D3 采集完整，D4 无未解规则，D5 无未解补丁，D6 已通过设备差分。因此**这次 demo 不需要模型调用也成立**。模型接口对下一类未覆盖混淆的价值，是缩短识别失败原因和设计新策略的过程；是否有效需要用新样本、调用成本与误提案率单独评估。
